# Decisions

| # | Decision | Why |
|---|---|---|
| 1 | One Cloud Run service, Angular bundled into Spring Boot | One container, one URL, no CORS, one deploy command |
| 2 | PostgreSQL constraints + conditional UPDATE in one transaction decide correctness | Correct under any number of Cloud Run instances; Redis later only reduces load |
| 3 | Cloud SQL Java Connector, private IP, `ENCRYPTED_ONLY` | TLS without managing certificates; no public IP |
| 4 | Secrets via `--set-secrets` env vars | No Secret Manager client code |
| 5 | BCrypt hash encrypted with Cloud KMS (AAD = username) | Interpretation of "passwords encrypted with AES/RSA" (pending, see below) |
| 6 | HS256 JWT via Spring Security resource server, 12h TTL | Stateless; logins stay off the 20:00 reservation hot path |
| 7 | Demo mode = `demo` profile (open time 00:00), no API override | Same rules and code path; cannot be bypassed by clients |
| 8 | Demo seeding in one transaction behind `pg_advisory_xact_lock` | Safe when several instances start at once |
| 9 | Business timezone `Asia/Ho_Chi_Minh`; window 20:00 → midnight for tomorrow | Pending, see below; both configurable |
| 10 | First-come-first-served decided by database-level competition | Pending, see below |
| 11 | One space per vehicle per day; a user may own several vehicles; no cancellation | Phase 1 assumption (pending, see below) |
| 12 | Unit tests (Mockito) separate from Testcontainers integration tests | `./gradlew test` needs no Docker or GCP |
| 13 | `DB_POOL_SIZE × max instances < Cloud SQL max_connections` | Avoid connection exhaustion when scaling (db-g1-small ≈ 50) |
| 14 | Reservation idempotency by natural key: `(vehicle, date)` + space, via `INSERT … ON CONFLICT DO NOTHING` | A retry of a successful request returns the original reservation instead of a 409; no idempotency-key table. Conflicts raise no SQL errors, so Hibernate error logging stays on |
| 15 | Flyway migrations are immutable once deployed | Schema changes go into new `V3+` migrations |
| 16 | Temporary DB failures → `503 TEMPORARILY_UNAVAILABLE` + `Retry-After: 1` | Pool exhaustion at 8 PM is load, not a bug; tells clients to retry, which is safe for idempotent reservations and deposits |
| 17 | Deposits require an `Idempotency-Key` header (UUID), `UNIQUE(user_id, idempotency_key)` in the ledger (V3) | Deposits have no natural key; a retried deposit is applied once. Required, not optional: a client that forgets it would silently double-credit |
| 18 | Reservation window checked before the DB transaction (`TransactionTemplate`, as in `AuthService`) | "Closed" answers at 19:59 never take a pool connection |
| 19 | Deploy gate runs unit **and** integration tests | Only the integration tests prove the concurrency, payment and idempotency rules |
| 20 | Integration tests run the real 20:00 config with a movable `MutableClock` and BCrypt cost 4 | Tests the shipped window rule and dates deterministically; the 150-user race stays fast |
| 21 | Package by layer (`controller`, `service`, `repository`, `entity`, `dto/request`, `dto/response`, `mapper`, `exception`, `security`, `config`, `event`); services return DTOs, never entities; no service interfaces | Conventional layout for an app this size; entities never leave the transaction (`open-in-view: false`, LAZY associations) |
| 22 | Every entity extends `AbstractEntity` (IDENTITY `id`, `@Version`) and is named `…Entity`; V4 adds the columns, a surrogate `id` for wallets and a BIGINT identity for spaces | One consistent identity and optimistic-locking scheme; `ArchitectureTest` enforces it |
| 23 | Spring Data JPA only; native SQL only for `INSERT … ON CONFLICT` (reservation claim, deposit) and `pg_advisory_xact_lock`, inside the repositories | JPQL cannot express them; a JPA insert would abort the transaction on a conflict and break decision 14 |
| 24 | Wallet balance changes stay single-statement conditional UPDATEs (JPQL) that also increment `version`; `@Immutable` dropped; no `clearAutomatically` | Hibernate 7 rejects HQL updates on `@Immutable` entities. No mutators + `@Version` keep stale wallets from being written; clearing would detach entities the caller still uses |
| 25 | Repository writes are `Propagation.MANDATORY` | Claim, debit and ledger entry are only correct inside the service's single transaction |
| 26 | V4 is backward compatible; the wallet `version` may lag while an older app version still serves traffic (it doesn't increment it) | Accepted: no code compares wallet versions, and balances are protected by the conditional UPDATE + row lock + CHECK in both versions |
| 27 | M3: Redis (Redisson 4.8, no Spring Data Redis) coordinates reservations in a new `concurrency` package (concrete classes, no interfaces): per-space `RFairLock`, **one** global `RPermitExpirableSemaphore` for reservation transactions, and a cache of committed reservations | FCFS per space across instances, a reservation load on PostgreSQL that does not grow with the instance count, and fast answers at the 8 PM peak. PostgreSQL constraints still decide every reservation. Separate deposit and read semaphores were tried and removed: more configuration and failure modes for little gain; HikariCP limits that work |
| 28 | Reservations fail closed (503) without Redis; deposits, seeding and all reads never touch Redis; the dashboard falls back to PostgreSQL (≤ 1 query/s per instance); lazy Redisson init, Redis outside the health groups | One concurrency architecture for reservations, no uncoordinated reservation writes reaching PostgreSQL. A Redis outage costs reservation availability only, never correctness, and never blocks deposits |
| 29 | The cache answers only from committed facts, exactly as the transaction would (same error precedence, replay). "Vehicle has no reservation" is trusted only for a sold-out date, validated entry by entry; otherwise one database read decides | Zero SQL for most rejections without in-flight counters, Lua or extra synchronization. The API contract is unchanged; parity is tested with an empty, warm and sold-out cache |
| 30 | Bounded waits (lock 10 s, permit 3 s, pool 3 s) and explicit leases (lock 20 s, permit 15 s) treated as soft limits; Redis `retryAttempts` 3 and 20 pre-opened subscription connections | A lease can expire under a slow holder: PostgreSQL serializes, and the pool is the hard limit. Lock wait 10 s: one space's queue drains ~3 ms per waiter locally, so 1,000 requests for one space need ~3 s. Redisson also uses `retryAttempts` to get the pub/sub subscription each lock waiter needs: 1 attempt left waiters asleep during bursts (found in testing) |
| 31 | Declarative transactions: coordination (`ReservationService`: Redis lock and permit, `@Transactional(propagation = NEVER)`) is separate from the transactional business logic (`ReservationBookingService`). `WalletService.deposit` is a plain `@Transactional` method again. Read queries called outside service transactions are `@Transactional(readOnly = true)` on the repository. `TransactionTemplate` stays only in `AuthService` (crypto before the transaction) and `DemoDataSeeder` (startup runner: advisory lock and loop in one transaction) | No self-invocation pitfalls. No connection is held while waiting for Redis (a nested call fails fast). Supersedes decision 18's mechanism for reservations, not its rule. `ArchitectureTest` allows only `ReservationService` to call the reservation transaction |
| 32 | Connection pool per instance ≥ the reservation permits, plus headroom for deposits and reads (startup WARN otherwise). 10 is the local starting value, not the GCP sizing | The budget is global, so one instance can hold every permit. Permits bound reservation transactions but do not reserve connections; all other database work shares the pool (full isolation would need separate pools) |
| 33 | M3 on GCP upgrades the existing environment: same application behavior, more capacity. Cloud Run 2 vCPU / 2 GiB, concurrency 200, min 1 / max 10 (the project's Cloud Run quotas in asia-southeast1: 20 vCPUs, 10 instances with Direct VPC egress); Cloud SQL `db-custom-2-7680`, `max_connections` 300; pool 10 and 10 reservation permits (the best local load test, `t-i5-p10-h10`); all other settings stay the `application.yaml` defaults; JVM options unchanged (Java picks G1 at this size). Memorystore Basic 1 GB is the only new resource | Simplest path; no separate environment to keep in sync. The settings were measured locally |
| 34 | `deploy.ps1` sets the maximum instances at both service and revision level (same value) and the minimum at service level only (revision-level minimum cleared) | Cloud Run applies the lower maximum of both levels: a hidden service-level cap of 3 limited the live revision, so both are now explicit and equal. The minimum precedence between levels is ambiguous, so only the service level is used; it changes without a new revision (min 8 for a load test, 1 otherwise) |
| 35 | Memorystore with AUTH (string in Secret Manager `redis-password`), `noeviction`, no persistence, no in-transit encryption for now | Private network only; `RedisConfig` has no TLS / CA settings; the TLS mode is fixed at creation, but recreating is cheap because Redis state is disposable. `noeviction`: the default `volatile-lru` could evict lock and permit keys (they have TTLs) |
| 36 | `deploy.ps1` refuses a deploy without Redis, or whose connection budget (max instances × pool × 2 + 10) exceeds Cloud SQL `max_connections` | M3 fails closed without Redis while its health check stays UP; the budget check catches deploying the M3 sizing before the Cloud SQL upgrade |

## Pending mentor confirmation

These are implemented with the defaults below. Each one is configurable or isolated, so a different answer means a small change.

| # | Question | Current behaviour | If the answer differs |
|---|---|---|---|
| A | Is "passwords encrypted with AES/RSA" satisfied by **BCrypt + Cloud KMS (AES-256-GCM)** encryption of the hash? | `stored = KMS.encrypt(BCrypt(pw), aad=username)` | Change only `PasswordCipher` / `AuthService` |
| B | Reservation window and timezone | Opens 20:00 **Asia/Ho_Chi_Minh** for tomorrow, closes at midnight | `RESERVATION_OPEN_TIME`, `RESERVATION_TIMEZONE`; closing rule in `ReservationWindow` |
| C | Does FCFS require **strict request-arrival ordering**, or is database-level competition acceptable? | **Resolved by M3 (decision 27):** FIFO per space, in the order Redis receives the lock requests; limits in `architecture.md`, "Ordering guarantees" | – |
| D | Can one user reserve several spaces with different vehicles on the same day? | Yes (limit is per vehicle) | Add a `(user_id, reservation_date)` unique constraint in a new migration |
| E | Cancellation / refunds? | Not supported | New feature |
